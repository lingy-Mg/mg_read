# 07 并发与性能规范

## 性能定义

MgRead 的“高性能、低阻塞、高并发”定义为：

- UI Isolate 不承担 Runtime 数据库、巨大插件数据编解码、校验、解压或同步 I/O。
- Node 事件循环不执行同步 I/O、无界计算或无界 fan-out。
- 每一层都有并发上限、队列上限、deadline、取消、背压和可观测等待时间。
- 大资源端到端流式传输，内存占用不随文件大小线性增长。
- 相同工作可在 Runtime 内合并、网络连接可复用、Runtime Store 写入可批处理。
- 性能先通过基线和 trace 定位瓶颈，再调整策略；不以更换协议或增加 VM 作为未经测量的默认答案。

首版不设发布阻断的固定延迟数字，但每次基线必须记录环境、数据规模、版本和分位数，能够与后续提交比较。

## 单 VM 的并发边界

Node JavaScript 在一个事件循环中运行；高并发来自同时等待大量网络/文件 I/O，而不是同时执行多个插件 JavaScript。Node Core 可以使用 libuv I/O Worker Pool，但插件不得创建 Worker、子进程或第二个 VM。

所有插件作者必须遵守 [Node.js 不阻塞事件循环原则](https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop)：

- 将工作拆成短小异步步骤并尽快让出事件循环。
- 禁止同步文件、同步压缩、同步 DNS/子进程和 CPU 密集正则/解析。
- 避免长 Promise 微任务链造成事件循环饥饿。
- 对输入大小设上限，解析成本随输入受控。
- 同步死循环无法由普通 `Promise.race`、deadline 或 `AbortSignal` 抢占；一旦发生，整个 Runtime 可能失去响应。

因此，首版可信插件模型同时承担“一个有缺陷插件可影响全部插件”的明确风险。诊断 watchdog 可以检测事件循环延迟并报告，但单 VM 约束下不能可靠地原地修复同步卡死。

## 调度器

### 优先级

从高到低：

1. `interactive`：用户当前等待的搜索、详情、目录、当前阅读资源。
2. `prefetch`：下一章/下一屏图片等短期预测工作。
3. `download`：用户显式离线下载和恢复传输。
4. `maintenance`：插件更新、全量校验、缓存清理和后台仓库刷新。

优先级不是绝对抢占。调度器使用加权公平/老化策略，低优先级等待时间达到策略阈值后获得配额，防止持续阅读完全饿死下载与维护。

### 三级有界队列

```mermaid
flowchart LR
    IN["Incoming Request"] --> GLOBAL["Global bounded queue"]
    GLOBAL --> PLUGIN["Per-plugin limiter"]
    PLUGIN --> ORIGIN["Per-origin limiter"]
    ORIGIN --> IO["ctx.http / resource stream"]
```

- **全局层**限制 Runtime 的活动请求、排队请求和活动字节流。
- **每插件层**防止单个插件占满事件循环与传输资源。
- **每源站层**遵守连接容量、远端限流和公平性。
- 队列满时立即返回 `overloaded` 和可重试提示，不能继续分配内存。
- 具体并发数不是插件可配置字段；由平台基线和远端策略决定，并可在诊断构建中调整。
- 调度等待时间计入总 deadline；出队前 deadline 已过期则直接 `timeout`。

### 任务成本与长任务

调度单元记录类别、插件、源站、估计/实际字节、队列等待和执行耗时。插件不能在一个调度槽中递归启动无界子任务；SDK 提供受控 map/batch 工具并限制并发。

`Promise.all(unboundedList)` 被禁止。应使用带并发上限、取消传播和逐项错误策略的 SDK primitive。

## 取消与 deadline

- 所有 SDK 方法、Runtime handler、`ctx.http`、缓存写入和下载步骤接收 `AbortSignal`。
- 父任务取消会取消尚未提交的子任务；共享资源只有最后一个消费者离开后才取消源传输。
- deadline 使用绝对时间贯穿 Runtime Facade → Internal Bridge → Node → Runtime Store/平台服务；每层保留清理预算并只能缩短。
- 取消是正常终态，不按 internal error 记录。
- 不可取消的平台操作必须在适配器中注明，并用有界并发隔离，防止取消风暴耗尽资源。

## `ctx.http` 规范

插件所有网络请求必须使用 `ctx.http`，由 Core 统一提供：

- HTTP keep-alive/连接复用和每 origin 连接限制。
- DNS、连接、首字节、整体 deadline 和闲置超时。
- 有限重定向与循环检测。
- 插件/源站作用域 Cookie，不记录 Cookie 值。
- `gzip/br/deflate` 解压炸弹保护和解压后大小上限。
- 字符集检测/声明、文本大小限制和流式字节响应。
- 只对幂等读取和安全错误执行有界重试，尊重 `Retry-After` 并加入抖动。
- 响应头白名单、MIME 校验、URL 脱敏和 trace 指标。
- 上游流到缓存/loopback response 的背压传播。

插件不得直接导入 Node 网络模块建立未管理请求，也不得覆盖全局代理/证书/连接池设置。特殊网络能力若未来需要，必须扩展 SDK，而不是开后门。

## 请求合并与缓存

- 合并键包含插件、源站、规范方法、远端 ID、版本、Range 和会影响结果的参数。
- 只有明确幂等且结果可共享的请求参与合并。
- 每个等待者保留独立 deadline/取消；最早 deadline 不能错误取消其他等待者。
- 对已完成小结果可做有上限短期去重缓存；大结果只缓存文件和元数据。
- 负缓存只用于明确 `not_found`/兼容性结果，并使用短、可配置 TTL；网络失败不长期负缓存。
- 缓存键、数量和字节都有上限，不能以“更快”为由引入无界 Map。

## HTTP 资源流内存模型

- 使用流式读取/写入和固定高水位，响应慢时暂停上游。
- 不调用读取完整 body 的便捷 API 处理图片、ZIP、下载或未来媒体。
- 不为多消费者各自复制整块资源；共享稳定本地文件或受控广播管线。
- 上游无 Range 时先安全落盘，不在内存拼接成可随机访问对象。
- 校验和随流增量计算；最终校验与原子提交前不对业务声明完成。
- 每个活动流、缓冲字节和临时文件进入配额与指标。

## 主项目 UI 性能边界

### UI Isolate

只执行：

- Widget 构建、布局、绘制。
- 小型不可变 view state 映射。
- 短时输入校验和轻量路由转换。

禁止：

- Runtime 数据库查询/迁移或 Runtime 文件扫描。
- 大 JSON/HTML/文本解析或正文分段。
- SHA-256、ZIP 解压、图片批量处理。
- 同步文件操作或等待 Runtime 启动的阻塞循环。
- 在 `build()` 发请求、写进度或订阅未释放资源。

### Runtime 之外的有界计算

- 插件 JSON/HTML、摘要、校验和大文本处理属于 Runtime；主项目若有纯 UI 的可序列化重计算，才可进入固定 worker 数的执行器。
- 队列满时产生背压或 `overloaded`，不能无限 spawn Isolate。
- 任务输入输出需要可复制/转移；大字节优先使用流或可转移数据，避免重复拷贝。
- 每个任务有 request generation、deadline 和取消；旧结果不得覆盖新页面状态。

### UI 更新

- 下载/事件进度合并到适合帧率的频率，不按每个网络 chunk rebuild。
- 大列表虚拟化并用稳定 key；目录按批加载，不一次把所有节点转换为 Widget。
- 图片解码尺寸贴近显示尺寸，内存缓存有界。
- 响应式布局复用语义主题和集中尺寸；键鼠 hover/focus 与触摸命中区域分别验收。

## Runtime Store 性能边界

- Runtime 在自有受控执行边界打开唯一存储执行器；主项目不创建 Drift/SQLite 影子库。
- 若 ADR-0010 的 SQLite 方案通过探针，分别验证 WAL/checkpoint；不得假定两个 WAL 数据库
  存在跨文件原子事务。
- 多条目录、书架刷新和检查点写入使用事务/批处理。
- 阅读进度由 Runtime 按书籍串行合并并降频，Runtime 生命周期切换触发 deadline flush。
- 稳定 envelope 索引服务于明确查询：书架排序、来源绑定、目录 revision/order、下载
  状态/优先级、缓存回收；易变字段留在作用域 JSON，派生索引必须可重建且有测量依据。
- Runtime Facade 返回页面所需投影，而不是让 UI 加载完整正文或所有关联。
- 记录队列等待、JSON codec/升级与后端执行时间，区分排队、解析和存储操作本身耗时。
- 迁移和大清理采用可恢复分段工作，不在启动/UI 临界路径全量执行。

## 过载与公平性

过载是可预期状态：

- 新的低优先级工作先被延迟或拒绝。
- 交互请求可使用预留槽，但仍受全局硬上限。
- 单插件连续错误或事件循环占用过高可进入有时间窗的断路/降速状态；不能静默永久禁用。
- 源站返回限流时，该 origin 单独退避，不冻结其他插件/源站。
- 内存/磁盘压力时 Runtime 停止预取和维护，暂停可恢复下载，保护当前阅读与 Runtime Store 提交。
- Runtime RSS/heap 超过诊断水位时记录快照并拒绝新增后台工作；首版不因此自动创建新 VM。

## 性能基线

M1/M3/M5 每阶段生成可比较报告，至少包含：

| 场景 | 记录内容 |
| --- | --- |
| 冷启动到 ready | 各启动阶段耗时、Node/Javet 版本、平台/架构 |
| 内部 WS RPC | 队列/执行/Runtime 内部服务分解，p50/p95/p99 |
| 搜索与目录 | 插件、源站、条目数、解析/Runtime Store/UI 投影分解 |
| HTTP 大文件 | 文件大小、峰值 RSS/heap、吞吐、慢消费者、取消释放 |
| Range | 首字节、随机位置、上游支持/落盘路径 |
| 下载恢复 | 检查点、重启、重复字节、最终摘要 |
| Runtime Store | 队列等待、事务耗时、批量规模、迁移/日志状态 |
| Flutter | build/raster 帧、卡顿、列表规模、图片缓存 |
| 公平性 | 多插件/多 origin 混合负载、交互延迟与后台进度 |

报告必须固定设备/模拟器、构建模式、数据 fixture、Node/Javet 版本和运行次数。首版只将其作为基线和回归证据，不设置统一发布阻断阈值；一旦团队采用阈值，应通过新决策记录说明设备、分位数和例外策略。

## Code Review 性能清单

- 是否引入同步 I/O、无限循环、长正则或无界集合？
- 是否有全局/插件/origin 三级上限和队列满行为？
- `AbortSignal`、deadline、客户端关闭是否传播到底层？
- 是否把二进制或大文本放入 JSON/Base64？
- 是否在 UI Isolate 做 Runtime 数据库、解压、校验或巨大解析？
- 是否产生 N+1、每 chunk DB 写或每事件 rebuild？
- 共享请求的取消/错误是否会误伤其他消费者？
- 是否记录了队列等待、字节与耗时，且没有敏感内容？
- 性能改变是否有同环境基线，而非主观“感觉更快”？
