# ADR-0001：每个应用进程只运行一个 Node VM

- 状态：Accepted
- 日期：2026-08-13
- 决策者：MgRead 项目

## 背景

插件是全部在线数据来源，需要处理许多并发网络、目录、图片、缓存和下载任务。候选模型包括：

1. 全部插件共享一个 Node Runtime/V8 Isolate/Context。
2. 每个插件一个 VM 或 Worker。
3. 每个插件一个独立系统进程。

后两者能改善 CPU 故障隔离，但会显著增加 Android 嵌入生命周期、内存、跨 VM 通信、Cookie/缓存共享、版本维护和进程监管复杂度。用户明确要求单 VM 是硬约束。

## 决策

- 每个 MgRead 应用进程任意时刻最多创建一个 Node Runtime、一个 V8 Isolate/Context。
- 所有插件和 Runtime Core 共享这一个 JavaScript 事件循环。
- 插件禁止 `worker_threads`、`child_process`、第二个 VM、Javet Engine Pool 和原生 Addon。
- Node/libuv 为平台 I/O 使用的 Worker Pool 可以存在，但不执行第二个插件 JavaScript VM。
- 高并发通过异步 I/O、流式传输、有界队列、连接复用、请求合并、公平调度和背压实现。
- 首版 Runtime 致命失败后不在同一应用进程静默创建替代 VM；所有在途任务失败，用户通过诊断后重启应用。

## 后果

正面：

- 三个平台共享简单、稳定的 Runtime Core 和业务协议。
- Android 只维护一个 Javet Runtime 和一个所属线程，降低内存与生命周期复杂度。
- 插件共享的调度、Cookie、缓存、连接池和诊断有唯一所有者。
- 不需要跨 VM 复制大型对象或维持多套模块状态。

负面与限制：

- 一个插件的同步死循环、灾难性正则、长微任务链或内存失控可能拖死全部插件。
- deadline 和 `AbortSignal` 只能取消合作式异步任务，不能可靠抢占任意同步 JavaScript。
- CPU 密集插件代码不能并行，吞吐目标只对非阻塞 I/O 成立。
- 插件公平性必须由 Core 的三级有界调度和 SDK 规则维护。
- watchdog 可以发现事件循环延迟，但不能保证在同一 VM 内恢复。

这些限制必须出现在插件规范、诊断页和性能报告中，不能用“超时”措辞掩盖同步代码不可抢占。

## 被拒绝的方案

- **每插件 Worker**：违反单 VM 约束；增加 Android 内存、调试和协议复杂度。
- **每插件进程**：隔离最好，但桌面/Android 的承载模型分裂，资源成本和分发复杂度过高。
- **CPU 重任务自动转 Flutter Isolate**：插件代码和闭包不能安全透明迁移，也会建立隐式第二执行语义。

## 变更条件

只有实测证明单 VM 无法满足核心用户场景，且用户同意改变硬约束时，才可提出替代 ADR。新 ADR 必须包含 Android 内存/生命周期、插件隔离边界、协议迁移、崩溃恢复和旧插件兼容证据。
