# ADR-0002：首版插件完全可信

- 状态：Accepted
- 日期：2026-08-13
- 决策者：MgRead 项目

## 背景

完整安全沙箱需要限制 Node 模块、网络、文件、CPU、内存、原生调用、宿主 RPC 和更新信任，并要抵抗 VM 逃逸与供应链攻击。在单 VM、跨桌面/Javet 的首版中，做出可证明的隔离会显著扩大范围；Node 的 `vm` API 本身也不是安全机制。[Node `vm` 文档](https://nodejs.org/api/vm.html)

首版来源限定为唯一官方仓库和用户主动选择的本地 ZIP，用户明确接受可信插件假设。

## 决策

- 插件被视为与应用所有者同等信任的代码。
- 首版不实现安全沙箱、权限强制、代码签名信任链、发布者身份认证或插件进程隔离。
- 插件清单中的 capabilities 只用于兼容性检查、UI 展示、诊断和未来治理，不构成安全授权。
- Runtime 的 loopback HTTP/WS 首版不交换令牌、不做请求鉴权。
- SHA-256 只用于下载/文件完整性和损坏检测，不表示发布者可信。
- 仍执行严格的 ZIP 路径/大小校验、SDK 网络入口、并发配额、输入上限、日志脱敏和数据库类型化 RPC；这些是可靠性与误操作防护，不宣称能约束恶意插件。

## 后果

正面：

- 首版能集中验证插件 API、Runtime 生命周期、资源流和产品闭环。
- 避免用不完整“沙箱”制造错误安全感。
- 官方仓库和本地 ZIP 走同一简单安装/更新机制。

风险：

- 恶意或被篡改插件可能读取 Runtime 可访问的数据、发起网络请求、耗尽资源或干扰其他插件。
- 单 VM 下同步恶意代码可让全部插件不可用。
- 同机其他进程理论上可能探测 loopback 端口；不可猜测 handle 和 bootId 不是认证。
- 站外插件生态扩大时，用户仅凭“官方仓库”标签可能错误推断安全审计程度。

产品和文档必须清楚写明可信假设。本地 ZIP 安装应显示来源与风险确认，但不伪装成权限弹窗。

## 被拒绝的方案

- **Node `vm` Context 作为沙箱**：官方文档明确不是安全机制，且不能覆盖网络/文件/CPU。
- **仅靠 capabilities 权限弹窗**：没有可强制执行边界时只是虚假保障。
- **首版签名但不做发布者治理**：只能验证字节来自某密钥，不能解决密钥身份、撤销、审核和恶意行为。
- **仅监听 loopback 即视为安全**：loopback 缩小网络暴露面，但不认证同机客户端。

## 变更条件

以下任一情况要求新 ADR 和威胁模型：开放第三方仓库、引入自动安装、进入应用商店、处理高价值账号/支付、默认远程遥测，或需要对插件实施文件/网络/宿主权限。替代方案必须同时覆盖签名/撤销、资源限制、隔离逃逸、兼容迁移和用户沟通。
