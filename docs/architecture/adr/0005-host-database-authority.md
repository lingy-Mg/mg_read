# ADR-0005：Flutter 数据库权威与 Node 文件职责

- 状态：Superseded by ADR-0008
- 日期：2026-08-13
- 决策者：MgRead 项目

## 背景

书架、目录、进度、书签、插件状态和下载任务需要事务、一致迁移和 UI 可恢复状态；大文件、图片和未来媒体需要由 Node 结合插件网络上下文流式写入。若 Flutter 和 Node 同时直接打开同一 SQLite，迁移、锁、类型和故障恢复会形成双写权威。

## 决策

- Flutter 的 Drift/SQLite 是插件安装记录、书架、目录、进度、书签、下载任务和设置的唯一权威来源。
- SQLite 在 Flutter 后台 Isolate 运行，使用事务、迁移、批处理、WAL 和必要索引。
- Node 永远不获取数据库路径，不直接打开或修改数据库。
- Node 管理二进制网络传输、临时文件、流式缓存和下载文件写入。
- Node 通过强类型 `host.storage.*` 反向 RPC 读取/提交必要状态，不暴露 SQL 或通用数据库 API。
- 文件使用临时写入、校验、同卷原子重命名，再用幂等 RPC 提交数据库记录。
- 启动恢复协调未提交对象、残留 `.part` 和缺失/损坏文件。

## 后果

正面：

- 业务数据有一个事务和迁移所有者，Flutter 页面可从 Repository 稳定恢复。
- Node 的插件/传输故障不直接损坏数据库。
- 阅读器状态、离线书架和插件缺失行为不依赖 Runtime 存活。
- 数据访问可以用领域端口和测试替身验证。

代价与风险：

- 文件与数据库之间存在提交窗口，需要幂等键、sidecar/命名约定和启动恢复。
- Node/Flutter 反向 RPC 增加一次控制面往返，handler 必须可重入且不能持锁等待。
- 下载进度事件与数据库状态可能短暂不同，UI 必须以 Repository/snapshot 重建。
- SQLite 后台 Isolate 和文件管理各自需要明确队列与生命周期。

## 被拒绝的方案

- **Node 直接拥有全部 SQLite**：Flutter 书架/进度与 UI 生命周期过度依赖 Runtime，平台集成和 Dart Repository 测试变差。
- **Flutter 直接下载所有文件**：失去插件 Cookie/header/Range/缓存上下文，形成双网络栈。
- **双方共享打开同一数据库**：产生双迁移、双类型、锁竞争和崩溃恢复不确定性。
- **只用文件系统，不用数据库**：查询、事务、迁移、进度合并和孤儿恢复难以可靠实现。

## 变更条件

若实测反向提交成为核心瓶颈，应先优化批处理、投影和提交频率。改变权威所有者必须新 ADR，给出数据库迁移、双写切换、崩溃一致性、离线阅读和回滚方案。
