# ADR-0009：稳定记录骨架与作用域化版本 JSON

- 状态：Superseded by ADR-0011
- 日期：2026-08-14
- 决策者：MgRead 项目
- 依赖：[ADR-0008](0008-standalone-plugin-runtime-boundary.md)

## 背景

MgRead 仍处于数据规范快速演进阶段。插件清单、书籍元数据、目录附加信息、阅读锚点、
下载检查点、设置和插件 KV 都可能继续增加、改名或废弃字段。若每个可选字段都成为
SQLite 列，开发阶段会产生大量低价值的容器迁移；若把所有内容都塞进无约束 JSON，
又会失去身份唯一性、关系完整性、排序、并发控制和可预测查询。

ADR-0008 已决定这些数据全部属于 `mg_read_runtime`。本 ADR 进一步固定 Runtime Store
内部的数据形态，不改变主项目只消费强类型 Runtime Facade 的边界。

## 决策

Runtime Store 使用“稳定记录骨架 + 作用域化版本 JSON”的混合模型：

1. 每条记录只有少量长期稳定的 envelope 字段：稳定 ID、资料域、记录类型、作用域、
   父记录/身份键、排序键、主要状态、文档格式版本、乐观并发 revision 和 UTC 时间。
2. 会随产品或插件演进的业务字段存入 `payload` JSON。JSON 的解释由
   `recordKind + scopeKind + formatVersion` 决定，不存在一个全局、无类型、无限大小的
   `Map<String, dynamic>` 数据袋。
3. 字段只有同时满足身份/引用完整性、常用排序过滤、并发正确性或完整性校验之一，才可
   提升为稳定列。标题、作者、封面扩展、来源附加信息、插件清单快照、语义锚点、书签
   上下文、下载检查点、设置和诊断上下文默认留在作用域 JSON 中。
4. 大正文、图片、ZIP、缓存和其他字节不进入 JSON/Base64。正文进入独立内容对象层，
   图片及其他大对象进入 Runtime 文件对象层；JSON 只保存受限描述和稳定引用。
5. Cookie、令牌或未来凭据等敏感文档在逻辑上仍是版本化 JSON，但落盘必须是加密
   payload；不得与普通 `payload_json`、日志或默认诊断导出混存。密钥来源和跨平台实现
   必须在能力实现前另行探针和审查。
6. 普通 JSON 采用严格 UTF-8 文本作为可移植基线。正确性不依赖数据库 JSON 扩展或其
   私有二进制格式；数据库 JSON 函数只能作为通过探针后的校验/派生索引优化。
7. `null` 与字段缺失语义不同；持久化整数若可能超过 JavaScript 安全整数范围，使用
   规范十进制字符串；时间使用 envelope 的 UTC 整数时间或文档规范明确的 UTC 表达。
8. 未识别字段在读写和升级中原样保留。主项目和插件不能提交任意 JSON Patch 或 SQL；
   所有写入仍通过版本化 Runtime capability、领域命令和 Store codec/validator 完成。

## 版本与迁移

版本分为两个互不混淆的轴：

- **容器版本**：只处理表、索引、稳定约束和文件布局，必须显式、事务化、可回滚或可从
  备份恢复。它应低频，但不能假装永远不存在。
- **文档格式版本**：按 `recordKind/scopeKind` 独立演进。读取旧版本时用纯函数升级链在
  内存中投影；通过校验后可用 revision compare-and-swap 做惰性 read-repair，或由有界
  后台任务批量修复。

旧 Runtime 遇到未来版本文档时必须保留原始字节、拒绝覆盖，并返回稳定的
`data_version_unsupported` 或只读投影；缺少升级器、校验失败或中途崩溃都不能销毁原文档。
开发阶段允许显式清空测试数据，但不得把自动删库当作正式迁移策略。

## 公开类型边界

动态 JSON 仅是 Runtime Store 的内部持久化格式。Runtime Facade 继续返回版本化、强类型
投影；`mg_read`、`novel_reader_ui` 和数据来源插件都看不到表名、JSON envelope、迁移器
或数据库连接。新增 UI 数据需求必须先成为 Runtime capability/schema，而不是让页面读取
动态 Map。

## 后果

正面：

- 开发阶段增加可选元数据通常只新增文档 codec/schema，不需要修改容器。
- 不同插件、资料域和聚合可独立演进，未知字段能够跨版本保留。
- 身份、排序、状态、revision 和大对象边界仍有稳定索引与一致性约束。
- Store 可独立生成旧版/未来版 fixture，进行属性、迁移和崩溃恢复测试。

代价与风险：

- JSON 不能消灭所有迁移；身份、索引、约束、加密和文件布局变化仍需容器迁移。
- codec 必须保留未知字段并限制大小、深度、键数量和数组长度，否则会产生静默数据丢失
  或资源耗尽。
- 需要维护文档格式注册表、升级链和派生索引重建逻辑。
- 不能依赖 SQL 直接检查所有业务约束，Store validator 与验收套件成为强制门禁。

## 被拒绝的方案

- **所有领域字段都是固定列**：开发期列迁移过密，插件扩展会污染核心表。
- **全部只有一个任意 JSON blob**：无法可靠索引目录、状态和 revision，也无法约束作用域、
  大小与引用。
- **把动态 Map 直接交给主项目**：破坏强类型 Facade，并把存储版本耦合扩散到 UI。
- **一个 JSON 文件保存整本书或整个资料域**：单次改写和崩溃窗口过大，无法按章节分页、
  事务更新或有界恢复。
- **依赖 SQLite JSONB 作为跨版本格式**：把数据绑定到具体 SQLite 能力与私有表示，不利于
  后端探针、导出和跨平台一致性。

## 变更条件

若实际基准证明 JSON 解析、记录骨架或派生索引是主要瓶颈，可提出替代 ADR，但必须同时
给出数据导出、未知字段保留、旧/未来版本兼容、跨平台恢复和独立 Store 验收方案。不能以
“少写一个 codec”为由把任意动态结构暴露给 UI 或插件。
